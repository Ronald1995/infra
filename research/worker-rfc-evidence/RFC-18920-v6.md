## Summary

`NPUWorker` currently inherits directly from `WorkerBase` and maintains its own
copies of many vLLM GPU Worker control flows. This RFC proposes inheriting from
`vllm.v1.worker.gpu_worker.Worker` (called `GPUWorker` below), then removing
duplicated overrides in stages grouped by interface type. Ascend-specific
device setup, memory management, communication, graph capture, and profiling
remain in vllm-ascend.

The intended result is that a fix or feature implemented entirely in an
inherited upstream Worker method becomes available after vllm-ascend upgrades
to that vLLM version, without a downstream copy of the change. Inheritance
alone does not make new ModelRunner contracts or CUDA-specific behavior work
on NPU.

**Current implementation decision (v6).** Consolidate direct inheritance and
interface quarantine in [#20865](https://github.com/vllm-project/vllm-ascend/pull/20865).
NPUWorker derives from GPUWorker and calls its actual constructor through
super().__init__(). Existing NPU method bodies, signatures and decorators stay
unchanged, including shutdown. Every other newly visible GPUWorker method or
property is explicitly overridden to raise NotImplementedError until its NPU
contract is validated. Only the profiler-validation and elastic-executor
construction hooks receive NPU implementations because parent construction
requires them. #20866 is superseded; its shutdown migration is deferred.
#20850 remains closed. There is no required Ascend implementation stack.

### Historical divergence inventory

The copies have already diverged. Each row is a reason that a one-line base
class change needs constructor/device review. Differences in retained overrides
are assessed when those overrides are migrated, without a separate Phase 0.5 gate.

| # | Interface | vllm-ascend at the analysis baseline | Analyzed upstream `Worker` | Consequence if inherited as-is |
| --- | --- | --- | --- | --- |
| 1 | `update_config` | Forwards to `model_runner.update_config` only | Replaces the shared config object on `vllm_config`, the Worker, and the ModelRunner | Runner may keep stale config references; worker/runner swap not synchronized |

| 5 | `execute_model`, `sample_tokens` decorators | No `@torch.inference_mode()`, no `@with_gpu_sync_check` | Both | Inheritance adds them; must confirm no NPU path relies on running outside `inference_mode`, and that the sync-check gate passes on NPU |
| 6 | `init_device` | Hand-copied DP local-rank shift and `assigned_physical_gpu_ids` asserts from upstream PR #45026, plus a device-ids exception | Native CUDA branch | Every upstream device-isolation change must be ported by hand — this has already happened once |
| 7 | Memory accounting | `requested_memory = total_memory * gpu_memory_utilization` | `request_memory(snapshot, cache_config, external_weight_memory)` | Memory accounting differs; the upstream helper cannot be inherited as-is |

| 10 | `execute_dummy_batch` | Adds `log_memory_stats()`, passes `skip_gdn_state_update=True` | Passes `randomize_inputs=self.randomize_dummy_inputs` | Ascend `_dummy_run` has no `randomize_inputs` parameter |

These differences motivate reuse, but they also prevent a one-line base-class
change. Upstream [`init_device`](https://github.com/vllm-project/vllm/blob/7020600b1db32f239611b037f07e0dc5268e5b4f/vllm/v1/worker/gpu_worker.py#L442)
currently accepts only CUDA. Its default sleep backend uses a CuMem-based
allocator, while Ascend uses NPU initialization, HCCL, CaMemAllocator, NPU
Graph, and specialized KV-cache allocation.

## Goals

1. Reuse upstream Worker orchestration where its contract is independent of
   the accelerator.
2. Remove downstream overrides once their Ascend behavior is represented by
   a smaller device-specific hook, backend, or ModelRunner method.
3. Receive upstream Worker-only fixes and features through normal dependency
   upgrades, with no downstream copy of those methods.
4. Make the remaining overrides explainable by concrete Ascend behavior.

## Non-goals

- Rework the full ModelRunner inheritance hierarchy.
- Promise that every new GPU Worker feature works on NPU automatically.
- Remove Ascend-specific KVPP, layer reuse, sparse KV offload, 310P memory
  policy, ATB warmup, NPU profiling, or device health checks.

## Design Principles

1. **Inherit orchestration; own device mechanisms.** The parent Worker should
   own common sequencing and state transitions. Ascend should own device
   selection, memory allocation, graph capture, HCCL integration, and policy
   that is specific to NPU.
2. **Measure reuse by removed overrides.** Calling `super()` from a copied
   downstream method does not ensure future upstream changes are inherited.
3. **Verify contracts before deleting overrides.** Check parameters, return
   values, initialized attributes, ModelRunner methods, and device assumptions
   for every inherited method.
4. **Prefer narrow upstream hooks.** When a common flow has one
   device-specific step, contribute a hook upstream and override that step
   rather than keep a downstream copy of the whole flow.
5. **State the inheritance boundary precisely.** Automatic adoption applies
   only to methods actually resolved from the parent, for a compatible vLLM
   version and ModelRunner contract.
6. **Keep overrides through the hierarchy change.** Retain existing Ascend
   behavior when adopting GPUWorker; reconcile a method's contract when its
   override is actually migrated or removed.
7. **Quarantine newly visible interfaces.** Apart from the two required
   constructor hooks, every newly visible GPUWorker method or property raises
   NotImplementedError until a focused migration validates its NPU contract.

## Implementation Plan

### Current entry point: GPUWorker Inheritance and Interface Quarantine — #20865

[#20865](https://github.com/vllm-project/vllm-ascend/pull/20865) combines the
inheritance entry point and the conservative interface boundary from #20866.
It targets main directly. #20866 is superseded; #20850, #20863 and #20864
remain closed without merging. Phase 0 tooling (#20684) is independent, and
the earlier #20868–#20871 drafts are not a prescribed merge sequence.

**Scope:**

1. Derive NPUWorker from the explicitly aliased upstream GPUWorker and call
   its actual constructor through super().__init__(), never WorkerBase directly.
2. Retain all existing NPU non-constructor methods, signatures and decorators.
   Do not migrate shutdown, execution, PP handle ownership, configuration,
   reload, loading, dummy batches, sleep/wake, memory or runner construction.
3. Implement only the two hooks required by parent construction:
   _validate_profiler_config and _make_elastic_ep_executor. NPU profiler
   validation accepts disabled/torch settings. The unsupported executor has
   no CUDA elastic-EP imports, thread pool or allocated resources.
4. Reject enabled GPU fault tolerance and missing constructor hooks before
   calling the parent.
5. Explicitly override all 29 other newly visible methods and properties
   at the pinned dependency to raise NotImplementedError, even if a GPU
   default merely returns None, False or an empty result. Preserve property
   descriptors for sleep_mode_backend and randomize_dummy_inputs.
6. Record the complete immutable boundary in UNVERIFIED_GPU_WORKER_METHODS.
   Tests execute every stub/property and compare the actual installed parent
   surface with NPUWorker declarations, detecting newly added upstream APIs.
7. Remove a stub and its inventory entry only after the corresponding NPU
   runner/device/version contract is validated. Update method-resolution
   checks with the focused migration.

Against Ascend baseline
[`28065346d`](https://github.com/vllm-project/vllm-ascend/tree/28065346d433f9d23157c77c2b5b79c959a61871),
all **54 existing non-constructor methods and decorators remain unchanged**.
The inherited constructor owns common state, while NPU-specific state and
existing initialization remain local. Existing shutdown is retained because
the unsupported executor has no resources and the sleep backend is uncreated.

**Dependency and rollout:** vLLM
[#65565](https://github.com/vllm-project/vllm/pull/65565) supplies the constructor
hooks. The review pin remains e9f031bed0d150e2bef4b1eaa29aa50061e89203, based
on verified 24420b7a. Consume the merged hook API and qualify/backport it for
the matched v0.33.0 lane before rollout. This is a vLLM API dependency, not an
Ascend PR stack. #20865 remains draft pending startup/serving qualification.

### Independent Follow-up Work

Once the hierarchy change is established, consider individual changes against
the then-current `main`, with focused contract evidence. There is no fixed
stack or requirement to resynchronize the earlier draft chain as part of
#20865.

- **Contract tooling:** remeasure the current V2/310P/Xlite surface and evaluate
  the standalone Phase 0 registry/guard proposal.
- **Inherited interface validation:** newly visible APIs start as explicit
  NotImplementedError stubs. Validate and remove them individually, including
  private helpers and default/no-op interfaces. Review common cleanup only in
  a focused follow-up; the current shutdown implementation remains unchanged.
- **Forwarding/configuration reuse:** remove individual equivalent overrides
  only after comparing configuration identity, signatures and runner behavior.
  Any config/reload/signature alignment belongs to that focused change.
- **RL, dynamic weights and sleep:** assess upstream state transitions and
  CaMem/HCCL semantics independently, preserving NPU validation and cleanup.
- **Execution reuse:** identify narrow hooks for SP, KV connectors, monitoring,
  pooling, sampling statistics and idle/GDN behavior before deleting execution
  overrides.
- **Runner factories, memory and lifecycle:** converge only where current
  upstream extension points cover the NPU mechanisms. Retain documented NPU
  device selection, memory policy, KVPP/layer reuse/sparse offload, graph
  capture, warmup, profiling and health checks where necessary.

The earlier draft numbers identify design work already explored; they are not
an agreed merge order. Future PRs should be scoped and reviewed independently.

## Validation and Rollout

For the consolidated #20865:

- Six portable tests pass, including all 29 method/property rejections,
  missing constructor hooks, enabled fault tolerance, profiler settings and
  executor shutdown boundaries.
- Source comparison confirms all 54 existing non-constructor methods,
  signatures and decorators match the Ascend baseline.
- Source-declaration checks confirm the quarantine exactly covers the parent
  surface. In-memory mutations adding an upstream API or removing a stub
  correctly fail the method-resolution guard.
- Runtime tests additionally check actual installed Worker method resolution
  and real parent construction with WorkerBase configuration setup replaced
  by a test double. These tests do not establish full NPU startup.
- Ruff and focused source checks pass. Full formatting and runtime limitations
  are recorded in the PR. The local runtime attempt fails loading PyTorch
  c10.dll with WinError 1114.
- Startup, serving, supported-version integration and NPU hardware validation
  remain outstanding; source/CPU checks are not hardware evidence.

Use local tests and normal CI. Run remote NPU validation only when explicitly
requested. Future migrations must supply their own contract, method-resolution
and supported-version evidence before removing a quarantine stub.

## Risks

| Risk | Mitigation |
| --- | --- |
| Parent constructor imports CUDA elastic EP or validates CUDA profiling | Use the upstream constructor hooks and the NPU executor/profiler implementations in #20865. |
| Parent constructor changes NPU-visible state | Call the actual constructor, review the state inventory and qualify startup/serving before merge. |
| Inheritance exposes unvalidated parent APIs or silent defaults | Explicit NotImplementedError stubs cover all newly visible interfaces; the parent-surface guard catches additions on dependency upgrades. |
| A retained override differs from a newer parent contract | Keep it local for this hierarchy change and verify its contract when a focused migration is proposed. |
| Dependency differs between verified main and the matched release | Qualify the required hooks against both adapted versions before rollout; fail clearly when hooks are absent. |
| A future override deletion changes decorators, runner calls or cleanup | Test the specific migration and method resolution in that independent PR. |

## Open Questions

1. How should the final vLLM #65565 constructor hooks be merged/backported for
   the verified-main and current release contracts?
2. Which quarantined interfaces should be validated first, and what runner,
   device and supported-version evidence is required before removing each stub?
3. For later focused migrations, should NPU config replacement, dummy-input
   randomization and memory accounting adopt the upstream contract or retain
   a documented NPU-specific behavior?

The intended inheritance benefit is limited to Worker logic actually inherited
and compatible with the current NPU runner and device mechanisms.
